# Приглашения на свадьбу: Workflow vs AI Agent

Решение 1 в репозитории - линейный workflow, где порядок шагов (база, фильтр на возраст, цикл по гостям, вызов LLM, сборка итогового массива) задан заранее.  LLM только пишет текст приглашения. 
В Решении 2 работает AI Agent с tool к Supabase. Он сам решает, когда идти в базу и как собрать результат. Требования ему задают system message и нода Structured Output Parser. 
Принципиальная разница между решениями в том, кто управляет ходом выполнения задачи. В первом случае все шаги строго заданы схемой, а во втором модель самостоятельно определяет порядок своей работы. 

Для production я бы выбрал линейный сценарий. Так формат и порядок гарантированы структурой, расход токенов предсказуем, а ошибку процесса можно отловить по конкретному шагу и гостю. наблюдения за итерациями показывали, что агент мог выдумывать дату, адрес и искажать email. Отчасти это обусловлено уровнем модели, но тем не менее, агента стоит брать только там, где набор действий меняется от запуска к запуску. Это не случай конкретного задания

Для мониторинга агента я бы анализировал историю Executions в n8n (входы, выходы и вызовы tool по шагам). Кроме того, настроил workflow обработки ошибок с аллертами в Telegram. На выходе добавил бы автоматическую валидацию: число приглашений должно быть равно числу гостей с возрастом 25+, у каждой записи есть guest_id, а в текстах не должно быть дат, адресов и плейсхолдеров. 
Для дополнительного этапа тестирования я бы подготовил набор тестовых гостей с крайними случаями (без партнера, без детей, родственник). 
В обоих решениях использована модель openai/gpt-oss-120b на Groq, данные хранятся в Supabase, оркестрация в n8n Cloud.

Если говорить о развитии проекта, я бы подключил генерацию писем или сертификатов в зависимости от требований.
