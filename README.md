# Приглашения на свадьбу: workflow против AI Agent

Решение 1 это линейный workflow: порядок шагов (база, фильтр age >= 25, цикл по гостям, вызов LLM, сборка массива) задан заранее, а LLM только пишет текст. 
В Решении 2 один AI Agent с tool к Supabase сам решает, когда идти в базу и как собрать результат, а формат ему задают system message и Structured Output Parser. 
Принципиальная разница в том, кто управляет ходом выполнения: в первом случае схема, во втором модель. 

Для production я бы выбрал линейный workflow, потому что формат и порядок гарантированы структурой, расход токенов предсказуем, а ошибку легко найти по конкретному шагу и гостю. Без жестких правил агент выдумал дату, адрес и исказил email, поэтому его стоит брать только там, где набор действий меняется от запуска к запуску, и всегда с проверкой результата. 

Для мониторинга агента я бы смотрел историю Executions в n8n (входы, выходы и вызовы tool по шагам) и настроил Error Workflow с уведомлением в Telegram или на почту. На выходе добавил бы автоматическую валидацию: число приглашений равно числу гостей 25+, у каждого есть guest_id, в текстах нет дат, адресов и плейсхолдеров. Дополнительно нужен набор тестовых гостей с крайними случаями (без партнера, без детей, родственник) и контроль лимитов провайдера. 
В обоих решениях использована модель openai/gpt-oss-120b на Groq, данные хранятся в Supabase, оркестрация в n8n Cloud.
